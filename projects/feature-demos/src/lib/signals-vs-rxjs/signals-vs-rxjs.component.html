10-Year Expert Interview Cheat Sheet — Signals vs RxJS

1. Core Paradigms

  • RxJS (Push): Producer pushes values down the stream. Consumer subscribes. Great for async events, coordination, complex multi-step pipelines.
  • Signals (Push-Pull): Signal notifies dependents it is dirty. Evaluation is deferred until someone actually reads the value (lazy pull). Zero wasted computation.
  • Interview tip: "RxJS is for coordinating events over time. Signals represent state that directly drives UI."

2. The "Glitch" Problem

  • RxJS glitch: combineLatest fires once per .next(). Updating two sources synchronously → intermediate emission mixes new A with old B (stale state).
  • Signals solution: The dependency graph (DAG) marks nodes stale. Re-evaluation happens only once, in topological order, when values are read. No intermediate state ever exists.
  • Interview tip: "RxJS needs debounceTime(0) or auditTime(0) hacks to batch updates. Signals guarantee glitch-free computation natively."

3. Subscription Management

  • RxJS leak risk: Every subscribe() must be cleaned up manually — use takeUntil(destroy$), DestroyRef, or the async pipe.
  • Signals auto-track: No subscriptions. The reactive context (template/effect) tracks dependencies at runtime. Cleanup is automatic when context is destroyed.
  • Interview tip: "Signals completely eliminate subscription boilerplate — a major source of memory leaks in large Angular codebases."

4. Interop API (@angular/core/rxjs-interop)

  • toSignal(obs$): Wraps an Observable in a Signal. Needs { initialValue } unless the Observable is guaranteed to emit synchronously. Must be called in an injection context.
  • toObservable(sig): Converts a Signal to an Observable. Emits asynchronously (after the current reactive flush) using an internal effect.
  • rxResource() (Angular 19+): Reactive async loader. Tracks a request signal and re-fetches automatically. Exposes .value(), .isLoading(), .error(), .status().

5. When to Use Each — Decision Guide

Scenario Use Signals Use RxJS
Derived UI state (totals, filtered lists) ✅ Preferred ❌ Overkill
Simple async HTTP request ✅ rxResource() ⚠️ Works but verbose
Complex multi-step async (retry, debounce, race) ❌ Not designed for this ✅ Preferred
Event coordination (WebSockets, UI events) ❌ No time dimension ✅ Preferred
Component state management ✅ Preferred ⚠️ Adds boilerplate
